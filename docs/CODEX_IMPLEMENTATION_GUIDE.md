# RPG3 Codex Implementation Guide

この文書は、RPG3 を「動く技術デモ」から「短く濃いブラウザRPG」へ育てるための Codex 向け実装指示書です。

RPG3 は、疑似3Dダンジョン探索、パーティ、戦闘、宝箱、鍵、回復泉、ボス、セーブ機能を備えた Wizardry 風ブラウザRPGです。現状の価値は「すでに遊べる骨格があること」です。次の目標は、遊び続ける理由、判断、キャラクターの役割、短編物語を加えることです。

---

## 1. 開発方針

### 目標

RPG3 は、大作RPGではなく、次のような短編RPGを目指します。

- 初回プレイ時間: 20〜40分
- 迷宮探索、パーティ判断、短編物語が一体化している
- 1回クリアできるだけでなく、もう一度潜りたくなる
- 古いRPGの緊張感を持つが、不親切さは再現しない
- ブラウザで手軽に遊べる

### 最重要コンセプト

> この4人で迷宮に潜る意味があるゲームにする。

キャラクターは単なるHPバーではなく、探索と戦闘に意味を持つ存在にすること。

---

## 2. ゲームデザインの核

### 現状の核

- 疑似3Dダンジョン
- ミニマップ
- 4人パーティ
- ランダムエンカウント
- 宝箱
- 星鍵
- 回復泉
- 霧王アステルとのボス戦
- localStorage セーブ

### 追加すべき面白さ

1. 探索中の判断
2. パーティメンバーごとの役割
3. 戦闘中の読み合い
4. 迷宮内イベントによる物語の断片
5. エンディング分岐
6. クリア評価と軽いリプレイ性

---

## 3. パーティ設計

既存の4人を、ゲーム上の役割に結びつけてください。

### リリウム / 灯守

役割:

- 探索ヒント
- 迷宮の気配を読む
- 危険なイベントの前に短い警告を出す
- 霧王や星鍵に関する物語の中心

実装例:

- 「調べる」時に、周囲の危険や未回収イベントの方向を示す
- 暗闇区画や霧の濃い区画で補助効果を発揮する

### オルガ / 戦士

役割:

- 前衛
- 防御
- 強行突破
- 壁や扉など物理的障害への対処

実装例:

- 戦闘中の「かばう」または「防御」
- 特定の脆い扉や崩落壁を突破できる

### セイ / 盗賊

役割:

- 罠解除
- 宝箱確認
- 逃走補助
- 隠し扉発見

実装例:

- 宝箱に「調べる」「開ける」「セイに任せる」を追加
- 罠解除成功率を持たせる
- 失敗時は小ダメージや敵出現などにする

### ミナ / 僧侶

役割:

- 回復
- 祈り
- 呪いや霧への対処
- 霧王を倒すことへの迷いを持つ物語担当

実装例:

- 戦闘中または探索中の回復スキル
- 回復泉や祠の効果を読み解く
- 状態異常を解除する

## 4. ロードマップ

### Sprint 1: 土台整理

目的: 挙動を変えず、今後の実装に耐える構造へ整理する。

タスク:

- README.md を追加または更新する
- docs/ROADMAP.md を追加する
- 現在の巨大JSを責務ごとに分割する
- データとロジックを可能な範囲で分離する
- 起動方法と動作確認手順を明記する

推奨構成:

```text
src/
  main.js
  state.js
  dungeon.js
  battle.js
  party.js
  events.js
  renderer.js
  ui.js
  save.js

data/
  dungeon.js
  enemies.js
  party.js
  events.js
```

注意:

- このSprintでは新機能を増やしすぎない
- 挙動維持を優先する
- セーブデータ互換性を壊す場合は移行処理を入れる

完了条件:

- 既存のゲームが従来通り起動する
- 探索、戦闘、宝箱、鍵、泉、ボス、セーブが動く
- 主要な責務が分割されている

---

### Sprint 2: 探索判断とキャラクター役割

目的: パーティメンバーを攻略上意味のある存在にする。

タスク:

- セイの罠解除システムを追加する
- ミナの回復または祈りを追加する
- リリウムの探索ヒントを追加する
- オルガの防御または強行突破要素を追加する
- 宝箱、扉、泉に選択肢を追加する

実装例:

```text
宝箱:
- すぐ開ける
- セイに調べさせる
- 無視する

泉:
- 使う
- ミナに祈らせる
- 今は使わない

扉:
- 鍵を使う
- オルガに押し開けさせる
- 迂回する
```

完了条件:

- 各キャラに最低1つ、探索中に意味のある能力がある
- プレイヤーがリスクとリターンで悩む場面がある

---

### Sprint 3: 戦闘改善

目的: 戦闘を単なる攻撃連打から、少し読むゲームにする。

タスク:

- 防御コマンドを追加する
- 逃走コマンドを追加する
- 敵の予兆行動を追加する
- ボス専用行動を追加する
- 回復または支援スキルを追加する

敵の予兆例:

```text
霧の僧兵が祈りを始めた。
次のターン、全体攻撃が来る。
```

完了条件:

- 戦闘中に毎ターン少し判断が発生する
- 予兆を見て防御や回復を選ぶ意味がある
- ボス戦が通常戦闘と違う体験になっている

---

### Sprint 4: 迷宮イベントと物語

目的: 迷宮を単なる通路ではなく、記憶に残る場所にする。

タスク:

- 固定イベントを10個以上追加する
- 壁のメモ、倒れた冒険者、祠、霧王の声などを追加する
- ボス前イベントを追加する
- エンディングを2種類以上追加する
- パーティ内の短い会話を追加する

文体方針:

- 短く、具体的に、不穏に
- 説明しすぎない
- 汎用ファンタジー語を避ける

避ける表現:

- 選ばれし者
- 古の封印
- 世界を救う勇者
- ただ悪いだけの魔王

推奨する物語方向:

```text
星霧地下迷宮は、かつて町を守るために作られた避難施設だった。
霧王アステルは単純な魔王ではなく、迷宮を守るために残された守護者だった。
三つの星鍵は封印を開く鍵であり、同時に何かを壊す鍵でもある。
```

完了条件:

- クリア後に「何の話だったか」を説明できる
- 霧王アステルに単純な悪役以上の意味がある
- プレイヤーが最後に選択できる

---

### Sprint 5: リプレイ性と仕上げ

目的: もう1回潜る理由を作る。

タスク:

- クリア評価を追加する
- 一部宝箱や敵出現を変化させる
- エンディング分岐を追加する
- 難易度を調整する
- スマホ操作を改善する
- 通しプレイで20〜40分に収まるよう調整する

クリア評価例:

```text
- 歩数
- 戦闘回数
- 倒れた人数
- 宝箱回収数
- 使用した薬草数
- 選んだエンディング
```

完了条件:

- 初回クリア後にリザルトが表示される
- 2回目に違う選択や違うルートを試す余地がある

---

## 5. 推奨サブエージェント構成

CodexまたはAIエージェントチームで分業する場合、以下の役割に分けてください。

### 5.1 Game Director Agent

責務:

- ゲームの面白さの統括
- スコープ管理
- 仕様肥大化の防止
- PRの方向性レビュー

判断基準:

- RPG3は短編RPGである
- 大作化しない
- キャラの役割がゲーム性につながっているか
- プレイヤーの判断が増えているか
- 不親切さではなく緊張感を作っているか

### 5.2 Code Architect Agent

責務:

- JS分割
- 状態管理整理
- データ駆動化
- セーブ互換性
- コード品質維持

注意:

- Sprint 1では新機能を追加しない
- 挙動維持を優先する
- グローバル変数を減らす
- 描画とロジックを分ける

### 5.3 Gameplay Systems Agent

責務:

- 戦闘
- 探索ルール
- アイテム
- 罠
- 宝箱
- 職業能力
- 成長要素

優先実装:

- 防御
- 逃走
- 敵予兆
- 罠解除
- 回復スキル

### 5.4 Dungeon & Level Design Agent

責務:

- マップ設計
- イベント配置
- 鍵と扉の導線
- 罠と報酬の配置
- 難易度カーブ

制約:

- 初期は12x12程度
- 3〜5分に1回は発見がある
- 行き止まりには報酬か情報を置く
- 理不尽な罠は禁止

### 5.5 Narrative & Character Agent

責務:

- キャラクター設定
- 迷宮内テキスト
- ボス前後イベント
- エンディング
- パーティ会話

文体:

- 短く
- 具体的に
- 少し不穏に
- 説明しすぎない

### 5.6 UI/UX & Feel Agent

責務:

- 操作性
- 戦闘ログ
- ボタン配置
- キーボード操作
- スマホ対応
- ダメージや回復のフィードバック
- 画面演出

判断基準:

- 今何が起きたか分かる
- 次に何ができるか分かる
- 操作が気持ちいい

### 5.7 QA / Playtest Agent

責務:

- 通しプレイ
- バグ検出
- セーブ/ロード確認
- 詰みチェック
- 難易度確認
- UI確認
- クリア時間測定

確認項目:

```text
- 初見で目的が分かるか
- 10分以内に面白い出来事が起きるか
- 鍵を取り逃して詰まないか
- セーブ/ロードで状態が壊れないか
- 戦闘が単調すぎないか
- ボスが理不尽でないか
- スマホで操作できるか
- 20〜40分でクリアできるか
```

## 6. PR運用ルール

### PRは小さくする

悪い例:

```text
戦闘、物語、UI、マップ、セーブを全部改善しました
```

良い例:

```text
敵の予兆行動を追加
宝箱に罠解除選択肢を追加
リリウムの探索ヒントを追加
```

### PR本文に必ず書くこと

- 目的
- 変更内容
- 動作確認手順
- 既知の制限
- セーブデータ互換性への影響

### レビュー観点

- ゲームとして面白くなっているか
- 既存機能を壊していないか
- スコープが大きすぎないか
- UIで何が起きたか分かるか
- 初見プレイヤーが詰まないか

## 8. Codexへの初回指示

最初にCodexへ依頼する場合は、以下の順番で作業してください。

### Step 1

リポジトリ全体を確認し、現在の構成、主要ファイル、起動方法、ゲームの機能を把握する。

### Step 2

README.md が不足している場合、以下を含むREADMEを作成する。

- RPG3の概要
- 起動方法
- 操作方法
- 現在実装済みの機能
- 今後の開発方針

### Step 3

現状の挙動を変えず、JSを責務ごとに分割する計画を作る。

### Step 4

小さなPRでリファクタリングする。新機能追加はまだ行わない。

### Step 5

リファクタリング後、探索、戦闘、セーブ、ボス到達が壊れていないことを確認する。

---

## 9. 実装時の注意点

- プレイヤーに理不尽な詰みを作らない
- セーブデータ破壊に注意する
- 画像アセットが読み込めない場合でも最低限動くようにする
- スマホでもボタン操作できるようにする
- ランダム性を入れすぎて調整不能にしない
- テキストを長くしすぎない
- 汎用ファンタジー表現に寄せすぎない
- まず短く完成させ、その後広げる

---

## 10. 完成イメージ

RPG3 の完成イメージは以下です。

> 星霧地下迷宮に4人で潜る、20〜40分の短編ブラウザRPG。  
> プレイヤーは宝箱、罠、泉、扉、戦闘で小さな判断を積み重ねる。  
> リリウム、オルガ、セイ、ミナにはそれぞれ攻略上の役割があり、物語上の迷いがある。  
> 霧王アステルは単純な悪役ではなく、最後にプレイヤーへ選択を迫る。  
> クリア後には評価が表示され、別の選択を試したくなる。

以上を守り、RPG3を「動く試作」から「記憶に残る短編RPG」へ育ててください。
